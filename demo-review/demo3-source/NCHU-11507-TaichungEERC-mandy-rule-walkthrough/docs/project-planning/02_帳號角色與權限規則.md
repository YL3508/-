# 帳號、角色與權限規則

> 本文用於選單、畫面、資料範圍、API 授權與測試帳號設計。`原案` 依需求書第 2 頁「（一）註冊及登錄方式」、第 4 頁「（四）競賽設定」第 1 點；`已決定` 依後續對話。

## 身分模型

| 身分／情境 | 登入與取得方式 | 可進入區域 | 重要界線 |
| --- | --- | --- | --- |
| 未登入訪客 | 不登入 | 公開網站、營隊報名 | 不進入學校或管理員工作區。 |
| 一般學校人員 | 學校人員以教育局 Open ID 登入並連結所屬學校 | 共用學校工作區的一般功能 | 使用教育部／教育局帳號也不因登入供應者而自動成為管理員；以所屬單位與授權判斷。 |
| 承辦學校指定人員 | 原有學校身分，加上管理員授予的承辦人角色 | 同一學校工作區的一般功能＋競賽承辦功能 | 保有一般學校報名等權限，不另換帳號。 |
| 系統管理員 | 教育局同仁及本校人員以相應 Open ID 登入取得管理員權限；非學校及教育局、無 Open ID 者由管理員設定帳號密碼 | 管理員工作區 | 管理員資格依人員／單位及角色，不以 Open ID 名稱字樣推定。 |
| 系統自動處理 | 非人員帳號 | 不作為網站工作區 | 泳道圖中承擔檢核、狀態、產檔與統計等系統動作。 |

「他校註冊為一般學校」在現有設計中指學校資料／人員帳號歸戶後取得一般學校權限；**是否有公開自助註冊頁**尚待確認，不可因名稱就新增一條未核定的學校自助註冊流程。

## 承辦授權的兩層關係

1. **學校層**：確認哪一所學校承辦競賽；學校仍可作為一般學校參賽。
2. **人員層**：系統管理員逐一授予該校指定人員「承辦人」角色；未獲授權的同校人員仍只有一般學校功能。
3. **操作範圍**：授權人員可管理該校承辦的所有競賽，不可僅因具有承辦角色就處理其他學校承辦的競賽。
4. **共用工作區**：登入後由系統顯示允許的 nav 項目；一般與承辦的共用功能只呈現一份，不複製頁面或上傳流程。
5. **後端核對**：每項承辦 API 至少核對登入者、承辦角色、所屬學校、競賽承辦學校及操作狀態。前端隱藏選單只改善操作體驗，不能代替授權檢查。

前兩層對應需求書第 2 頁「（一）」第 2 點與第 4 頁「（四）」第 1 點；「所屬學校承辦的所有競賽」為專題決議。若未來要逐場指定人員，須另立變更紀錄。

## 功能權限概覽

符號：`讀`＝瀏覽；`寫`＝建立／修改／送出；`設`＝設定規則；`—`＝未授權。表中的權限仍受資料歸屬、期限及狀態限制。

| 功能 | 訪客 | 一般學校 | 承辦指定人員 | 管理員 |
| --- | --- | --- | --- | --- |
| 公開頁、已公開公告／資源 | 讀 | 讀 | 讀 | 讀／設 |
| 自己學校資料與報名 | — | 讀／寫 | 讀／寫 | 管理設定；代填待確認 |
| 指定對象調查表 | — | 受指定時寫 | 受指定時寫 | 設／讀／匯出 |
| 教學資源與成果照片 | 依公開設定讀 | 寫 | 寫 | 設／可上傳／打包下載 |
| 承辦競賽建立、報名審核、抽籤及成績 | — | — | 所屬學校承辦競賽的寫 | 授權／新增所需欄位；代辦待確認 |
| 參賽學校報名及補件 | — | 自己學校寫 | 自己學校寫 | 代辦待確認 |
| 計畫填報與經費概算 | — | 自己學校寫 | 自己學校寫 | 設／兩階段審查／匯出 |
| 營隊報名 | 寫 | 可作訪客流程 | 可作訪客流程 | 設／匯出／活動後刪除報名紀錄 |
| 網站頁面、公告、跑馬燈與帳號 | 讀公開內容 | — | — | 設／寫 |

## 權限判斷順序（專題設計）

1. 確認是否登入；訪客流程另行處理。
2. 辨識登入來源與所屬單位，查系統中的人員及學校關係；不要只憑電子郵件尾碼或前端傳來的角色字串。
3. 依管理員、一般學校、承辦人等角色決定可見選單。
4. 執行業務操作時，再查資料歸屬、指定對象、時間窗、名額及目前狀態。
5. 拒絕時回傳可理解的原因；是否顯示「鎖住的承辦選單」尚未要求，目前採**未授權則不顯示**。

## 待確認

- 同校報名與審核的迴避規則，尤其同一人審自己送件的案件。
- 人員換校、停用、承辦權限撤銷及歷史資料如何保留。
- 正式 Open ID 的欄位、介接方式；專題測試帳號不得被說成正式 Open ID 已完成。
- 無 Open ID 管理員帳號的建立、密碼重設與停用細則。
