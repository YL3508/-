## 來源與判讀順序

1. **需求書原案**：使用者提供的《臺中市英語教育資源中心網站建置委託資訊服務案系統建置需求說明書.pdf》。頁碼指 PDF 印在頁面上的頁碼，主要為第 2–6 頁。
2. **使用者已確認的專題決議**：本次對話中明確確認的範圍、角色、網站架構與交付目標；若與需求書原案不同，兩者都要留痕並寫明專題採用方式。
3. **小組共同討論文件**：使用者提供的《英語教育資源中心_專題決策紀錄.md》。其中標為「已決定」的內容，仍須檢查是否與後續使用者確認事項一致。
4. **既有圖稿**：泳道圖與網站地圖用來對照流程和畫面，不單獨作為未寫明業務規則的核定依據。
5. **合理補充／待確認**：沒有原文或明確決議支撐的設計，不得寫成已確定需求。

同一議題若有先後不同的說法，以**較晚且明確的使用者決議**作專題目前版本；保留原說法及變更日期。文件內的「計畫日期」不等於實際完成日期。

## 狀態標籤

| 標籤 | 意義 |
| --- | --- |
| `原案` | 需求書明載；不表示專題已完成。 |
| `已決定` | 使用者已在對話中明確確認的專題處理方式。 |
| `已更新`／`已釐清` | 已決定事項的後續修正或更精確界定；須記錄被取代的說法。 |
| `小組紀錄` | 附件中的小組討論內容，尚未由本次對話逐項核定。 |
| `暫定` | 目前可先設計，但須保留可調整性。 |
| `規劃` | 對未來作業的安排，尚非實際完成紀錄。 |
| `待確認` | 規則、責任、欄位或時點仍未明確。 |
| `實際` | 有可核對的完成日期或成果證據；不得由預計日期推定。 |

## 更新方式

1. 先在 `01` 更新決議、來源、決議日期及被取代的說法。
2. 再更新受影響的角色、畫面、流程文件；不要只改圖或只改排程。
3. 若變更影響 ERD、API、測試或工期，在 `05` 的檢查項與 `06` 的差異紀錄留下對應編號。
4. 未取得成員進度回報時，`06` 的實際日期保持「未回報」。
