# 後續產出指引

> 給小組與後續 AI 指令使用。目的是讓網站地圖、泳道圖、ERD、API、畫面、程式與測試對同一套規則；本檔不預先核定資料表名稱、端點路徑或未決業務規則。

## 指令前先提供的基準

提出新任務時，至少指出：

1. 要產出的成果類型與格式，例如網站地圖 PNG／SVG、ERD 草案、OpenAPI、Vue 畫面或測試案例。
2. 應以 [01_專題決策紀錄.md](01_專題決策紀錄.md) 的目前生效規則為準，並參照 [02](02_帳號角色與權限規則.md)、[03](03_網站架構與畫面規則.md)、[04](04_功能流程與業務規則.md)。
3. 需要涵蓋的模組、角色及資料範圍；若只做部分模組，明寫範圍。
4. 對未決事項採何種處理：標 `待確認`、提出選項，或由小組提供新決議；不要默默替團隊定案。
5. 若使用既有圖稿，指定目前版本，不以舊版四區網站地圖覆蓋共用學校工作區的決議。

## 各成果的必要核對

| 成果 | 核對重點 |
| --- | --- |
| 網站地圖 | 一張總覽＋三區細圖；一般與承辦共用學校工作區；nav 權限顯示；頁面／檢視與區塊／功能註記分開。 |
| 泳道圖 | 訪客、一般學校、承辦學校、管理員、系統自動處理五欄；承辦可使用一般功能；判斷菱形、通過與未通過路徑及返工箭頭清楚不重疊。 |
| ERD | 人員與學校分開；學校承辦身分與指定人員角色分開；競賽歸屬、報名、附件與審核歷程、調查指定對象、資源類型、計畫兩階段審查、營隊場次與報名等均有可追溯關係。未決資料粒度須註明。 |
| API | 每個端點明確列登入要求、角色、學校／競賽資料範圍、期限／狀態檢核與錯誤分支。不得只靠 Vue 隱藏選單；不能把管理員代辦權限自行加入。 |
| Vue 畫面 | 保留共用版型，nav 切換 main 檢視；承辦選單僅授權人員可見；一般功能不重複做兩份；公告詳情有獨立分享入口。 |
| 測試案例 | 至少覆蓋未登入訪客、一般學校、具承辦權限人員、管理員；測正反分支、跨校存取拒絕、期限／名額、補件迴圈、公開範圍。 |
| 報告 | 區分需求書原案、專題實作、測試資料模擬及未完成／待確認事項；進度以 [06_專題排程_計畫與實際.md](06_專題排程_計畫與實際.md) 的實際欄為準。 |

## 跨模組的不變規則

- 非學校及教育局、無 Open ID 的管理員設定帳密登入路徑須保留；學校人員仍以 Open ID 為原案。
- 管理員先指定承辦學校，再逐一授權該校指定人員；承辦者保有一般學校功能，可處理所屬學校承辦的所有競賽。
- 調查表由管理員指定可填學校；資源與照片由所有已註冊學校上傳；照片／資源共享上傳流程但保留不同資料類型。
- 競賽審核與補件由承辦者操作；管理員主要負責授權與按需求新增報名、指導及行政支援欄位。代辦權限未定。
- 計畫兩階段審查由管理員執行；營隊允許訪客免登入報名。
- 原 P0／P1／P2 不作 10/13 功能刪減依據；全部模組可操作是目標，實際完成需測試證明。

## 可直接重用的任務描述範例

> 請依 `docs/01_專題決策紀錄.md` 至 `docs/04_功能流程與業務規則.md` 的目前有效決議，為「競賽報名與補件」產出 ERD 與 API 草案。分開標示需求書明載、專題已決定及待確認內容；承辦人員須同時具有一般學校權限，所有承辦操作須檢查所屬學校與競賽歸屬。不要假定管理員可代審，也不要把同人自審寫成已核定規則。列出必要的正反測試案例。

若新決議與文件相衝，先在決策紀錄留下變更，再改圖稿與設計；不要只依一張最新圖片反推所有業務規則。
